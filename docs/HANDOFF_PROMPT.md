## 2. Железо и окружение (измерено)

- AMD Ryzen 9 7950X3D, 16 ядер / 32 потока, AVX-512F/BW/VL/DQ/VNNI/BF16, F16C, AVX2, FMA.
- **Асимметрия кэша**: только CCD0 (`cpu0-7,16-23`) имеет 96 MiB 3D V-cache; `cpu8-15,24-31` — обычные. Поэтому все бенчмарки **пиннить через taskset**, иначе разброс 10-30%.
- DRAM ~**78 ГБ/с** на всех потоках, 43-65 ГБ/с на одном потоке (измерено с data-dependent sink; без него компилятор выбрасывает чтения и получаются фантастические 700+ ГБ/с).
- GPU: RX 7900 XT, 20 GiB, ROCm 10.1 в `/opt/rocm`. **Сейчас CPU-only.** GPU — отдельная будущая фаза роадмапа.
- Arch Linux, sudo-пароль `ilovedonuts` (у пользователя спрашивать не нужно, но злоупотреблять не надо).

### КРИТИЧЕСКИ ВАЖНО: машина делает hard reset
Машина несколько раз уходила в **жёсткий reset под многочасовой нагрузкой всех ядер на пропускную способность памяти**. Причины не найдены (не OOM, не MCE, не троттлинг; подозрение на PSU/VRAM стабильность). Правила:
1. Не запускать многопоточные бенчмарки на гигабайтных буферах без нужды.
2. Тяжёлое — только через `flock /tmp/kata-bench.lock` и с `KATA_DUTY` (по умолчанию 0.90) и `KATA_MAX_THREADS`.
3. **После каждого reset** проверить `find build -size 0 -type f` — reset во время линковки оставляет нулевые бинари, а ninja рапортует «no work to do», и бинарь молча ничего не выводит. Лечение: `rm -rf build && cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release`.
4. Сообщать пользователю про выросший `user time` — именно он греет железо.

## 4. Архитектура кода (5039 строк, всё в `/home/medovarov/kata`)

```
include/kata/  types.h quant.h gemv.h gemm.h norm.h rope.h attn.h prefill.h shortconv.h
               sampler.h gguf.h model.h pool.h backend.h cpu.h simd.h throttle.h
src/           quant.cpp gemv.cpp gemm.cpp norm.cpp rope.cpp attn.cpp prefill.cpp
               shortconv.cpp sampler.cpp gguf.cpp model.cpp pool.cpp backend.cpp cpu.cpp
run/           kata_run.cpp
bench/         bench_gemv bench_gemm bench_k4 bench_attn bench_rope bench_norm
               bench_real_weights bench_vs_ggml
tests/         test_{quant,gemv,gemm,norm,rope,attn,prefill,shortconv,sampler,pool}.cpp
scripts/       coverage.sh coverage.py
```

Ключевые слои:
- **Kernels** (`gemv`/`gemm`): q4_0, q8_0, q4_K, q6_K. Каждый kernel несёт свой `__attribute__((target(...)))`, поэтому один бинарь работает везде и выбирает путь в рантайме (`cpu_isa()` → `Isa::{Scalar,Avx2,Avx512Vnni}`).
- **GEMM**: VNNI-микроядро `q4_K_vnni_tile` (8 строк × 16 токенов, `_mm512_dpbusd_epi32`), `q6_K_vnni_tile` (bias −32 складывается в тот же `mullo`, что и масштаб — это единственный способ не потерять 39%, см. EXP-0026 vs EXP-0029).
- **Backend boundary** (`backend.h`): `Backend` с `rms_norm`, `rope`, `gemv_q4_K_q8_K`, `gemv_q6_K_q8_K`. Ядро входит в интерфейс только когда имеет реальную реализацию (пустых заглушек не бывает — они дают правдоподобный мусор).
- **Model** (`model.cpp`): `Impl` с `forward(token, st)` (однотокенный decode) и `prefill(tokens, n, st)` (чанками по `ubatch`). Все скретч-буферы — члены `Impl`, аллокаций в горячем пути нет.
- **ThreadPool** (`pool.cpp`): spin-then-park, воркеры крутятся на атомарном `generation` с адаптивным бюджетом (4× наблюдённый интервал между fan-out, пол 8 мс, потолок 20 мс, env `KATA_SPIN`), `cv_start` нотифицируется только если `sleepers != 0`.

### Переменные окружения
`KATA_MAX_THREADS` (потолок потоков), `KATA_DUTY` (скважность, 0.90), `KATA_SPIN` (µs спина), `KATA_UBATCH` (по умолчанию 1024), `KATA_PROF=1` (послойный профиль), `KATA_DUMP=<dir>` + `KATA_DUMP_POS` (дампы тензоров, каталог надо `mkdir -p` заранее).

### Сборка и тесты

## 5. Главные правила и принципы

**Процесс.**
1. Одна задача за итерацию. Задача достаточно мала, чтобы её можно было реализовать, проверить и измерить.
2. Гипотеза формулируется ДО реализации, с ожидаемым эффектом и способом проверки. Если гипотеза провалилась — она записывается как провалившаяся, с уроком.
3. Каждая итерация оставляет рабочее состояние: сборка + тесты зелёные.
4. Изменение производительности без бенчмарка не существует. Всегда сравнивать с baseline на **том же бинаре/железе/пиннинге**, минимум 3 прогона, смотреть разброс.
5. Сначала атрибуция, потом оптимизация: `perf record -g` / пофазные таймеры, чтобы знать, куда уходит время, а не угадывать.
6. Правило Амаля: прежде чем оптимизировать ядро, проверить, что доля этого ядра вообще позволяет выиграть. Половина «медленных ядер» в этом проекте оказывалась не там, где время.
7. Не копировать llama.cpp. Читать его исходники, понимать механизм, реализовывать **своё**, объясняя, почему это лучше или хотя бы равно.

**Код.**
- C++20, `-Wall -Wextra -Wpedantic -O3`. Соблюдать `cpp-coding-standards`: RAII, `const` по умолчанию, `enum class`, никаких C-style cast, никаких сырых `new/delete`, `nullptr`, `'\n'`, `[[nodiscard]]`, именованные lock_guard, никаких магических чисел.
- Логирование — по `logging-best-practices`: одно широкое структурное событие на запрос, а не россыпь строк.
- Новый нетривиальный код (ветка, цикл, парсер, деньги/безопасность) — с тестом. Тест обязан проверять значение, а не факт вызова.
- Численные ядра: сверять с эталоном на граничных формах (m < MR, m % MR != 0, нечётные размеры, нулевые тензоры).
- Комментарий объясняет **почему**, а не что. Шорткат с известным пределом помечать `shortcut: <предел>, <когда обновлять>`.
- Никаких заглушек-пустышек, которые «просто ничего не делают»: они дают правдоподобный мусор.

**Эксперименты.** Каждый получает `EXP-NNNN`, статус (`PASSED`/`FAILED`/`REJECTED`/`DEFERRED`/`NEEDS_RESEARCH`), строку в сводной таблице и развёрнутый разбор в `docs/experiments/EXPERIMENT_LOG.md`: проблема → гипотеза → реализация → измерения до/после → анализ → вывод → следующий шаг. Отрицательные результаты хранятся навсегда, с ними сверяются перед новой попыткой (многие идеи уже отвергнуты с числами — не повторяй их вслепую).

**Git.** Коммит на итерацию, осмысленное сообщение `EXP-NNNN: суть (было -> стало)`. Пуш: `git push origin dev && git push origin dev:main` — `main` и `dev` держатся идентичными. Никогда не смешивать экспериментальное изменение с несвязанным рефакторингом.

**Общение с пользователем.** Пользователь пишет по-русски, отвечать по-русски, коротко и по делу, с числами. Он просил: «получаешь значимый прирост — пишешь мне». Не растекаться в рекомендации; если застрял — останавливаться и говорить, что именно не так, а не молча бурить два часа.

## 8. Общая цель проекта (чтобы не потерять горизонт)

1. Сейчас: CPU-only движок, обгоняющий llama.cpp по prefill и decode на этом железе, затем — собственные идеи, которых у llama.cpp нет (квантование KV, MoE-кэш экспертов с предсказанием, короткие форматы весов, альтернативные архитектуры блоков).
2. Потом: GPU-бэкенд через `Backend`-интерфейс, ROCm/HIP. Архитектуру держать расширяемой, но GPU не трогать до явной команды.
3. Дальше: MoE-движок с кэшем/офлоадом экспертов, квантизация KV, экспериментальные архитектуры (SSM-замена блоков, low-rank, pruning) с обязательной оценкой качества (perplexity / согласие с полной моделью).
4. Продукт: работающий движок + воспроизводимые бенчмарки + профилировщик + покрытие тестами ≥75% + журнал экспериментов как основной интеллектуальный актив проекта.
5. Не забыть то, чего в репо ещё нет: `docs/research/COMPETITIVE_ANALYSIS.md` (сравнительный анализ vLLM, SGLang, Strata, llama.cpp, openset-llm).

Начинай с раздела 7, шаг 1.

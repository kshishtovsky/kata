# EXP-0066: prefill attention is ALU-bound; PV is 60% of it

Status: PASSED (measurement). No code change — this closes a family of
hypotheses rather than adding a speedup.

## Question

Attention core is 50% of a 16k prefill (`core 1479 + 1655 + 630 ms` across the
three logged chunks, `mix 2044.5` of a `4218 ms` chunk). Every optimisation
proposed for it in this project has assumed a resource: bytes (KV int8, tiled
layout, prefetch, head-major) or instructions (register tiling, ILP, hadd).
EXP-0056 suggested instruction-side. Nobody had measured which resource binds.

## Probe 1 — footprint sweep at fixed instruction stream

`/tmp/atr.cpp`: the shipped `prefill_group4` call on a 256-token block, with the
K/V pointers re-aliased onto a window so the addressing pattern is identical and
only the resident footprint shrinks.

| resident K/V window | time | rate |
|---|---|---|
| 1024 positions (1 MB) | 37.4 ms | **28.7 GMAC/s** |
| 4096 (8 MB) | 158.3 ms | 27.1 |
| 8192 (16 MB) | 321.3 ms | 26.7 |
| 16384 (64 MB) | 642.7 ms | 26.7 |

A 64x change in footprint moves the rate by 7%. **Nothing here is
traffic-bound.** That retires, for prefill attention: KV quantisation, the
transposed/tiled K buffer, prefetch tuning and head-major layout tuning. All of
those pay only by cutting bytes.

## Probe 2 — ablation

`/tmp/abl2.cpp`: the same kernel with one component switched off, single core,
16384 positions, 64 query rows.

| variant | time | rate | delta |
|---|---|---|---|
| full | 106.2 ms | 20.2 GMAC/s | — |
| no 4-way hadd (lane 0 only) | 87.0 | 24.7 | +22.1% |
| no exp | 82.8 | 25.9 | +28.4% |
| no PV | 42.1 | 51.0 | **+152.1%** |
| QK only | 42.1 | 51.0 | +152.5% |
| V hoisted out of the head loop | 106.3 | 20.2 | −0.0% |

- **PV costs 64 ms against QK's 42 ms for the same 16 FMAs per position**, so it
  is not FMA-throughput that binds PV but the `acc[4][4]` loop-carried chain plus
  the broadcast feeding it.
- Hoisting the V load out of the per-head loop is **free already** (compiler or
  L1). That was the EXP-0016 trick; it is spent.
- The softmax feed (4-way hadd + exp) is 28-34% and the two overlap.

## Verdict

The only remaining levers are instruction-side: fewer operations per position,
not fewer bytes. Concretely that means either fewer live accumulators (2 heads
per pass, paying 2x V loads) or an algorithm that does fewer MACs
(int8 `vpdpbusd` at 311 GMAC/s per core against 80.5 fp32 — 3.9x on paper, and
the first *lossy* lever on this stage, so it needs its own PPL gate), or a
different attention shape entirely, which is a training question.

Recorded so the next iteration does not re-propose a traffic fix.

## Addendum: head-group width is not a lever either

`/tmp/g2.cpp` runs the same kernel with `G` query heads per pass (4 is correct
for LFM2.5: 32 query heads over 8 kv heads). Single core, 16k, 64 rows:

| G | time | rate |
|---|---|---|
| 2 | 420.4 ms | 5.1 GMAC/s |
| **4 (correct)** | 119.5 | 18.0 |
| 8 | 77.8 | 27.6 |

G=2 pays a second full position walk per kv head and loses 74%. **G=8 is 40%
"faster" only because it is numerically wrong** — it spans two kv heads and
indexes both through one `kvh`. The apparent win is the per-pass loop overhead
being amortised over twice the heads, which is not available inside the correct
GQA shape. So there is no head-grouping tuning left: 4 is both correct and the
best correct value.

## Addendum 2: the PV cost is not the broadcast, and not the V load

Four probes on the PV loop, single core, 16384 positions, 64 rows:

| variant | time | delta |
|---|---|---|
| full | 104.2 ms | — |
| `V=K` (reuse the already-loaded K as the value) | 105.7 | **−1.4%** |
| V-hoist (load once, share across 4 heads) | 104.1 | +0.1% |
| `no-bcast` (one broadcast reused for all 4 heads) | 76.7 | **+35.9%** |
| broadcast from register instead of stack round trip | 104.2 | 0.0% |

The `V=K` result is the decisive one: **removing the V load entirely changes the
time by 1.4%**, so the 60% PV cost is not memory. And `no-bcast` is not measuring
the broadcast either — it collapses four FMA streams into one (4 FMAs per `r`
instead of 16), so it is measuring arithmetic.

The stack-round-trip hypothesis is also refuted, and instructively: object code
of the shipped `prefill_group4` already contains **18 `vbroadcastss` and zero
`vmovups` to `(%rsp)`** — GCC was already keeping the four probabilities in
registers. Rewriting the loop to broadcast explicitly from an `__m128` (which is
what the source now does) compiles to the same code and measures the same
104-106 ms.

So PV's cost is 16 FMA plus 4 broadcasts per position over 16 accumulators, and
the kernel is at **0.10 zmm-FMA/cycle against Zen 4's 2.0** — a 20x gap that no
loop-level rearrangement has moved in five attempts (register tiling, ILP
chains, V hoisting, broadcast form, chain splitting). The remaining explanations
are at a different level: the accumulator set is 16 zmm plus temporaries, and
each position's 16 FMAs all target those registers while the next position's
loads and the shape comparisons compete for issue slots. That is a different
kernel, not a tweak.

## Ceilings for the two proposed priorities

Both were measured before implementing, per the standing rule.

**Persistent MoE dispatch (proposed priority 1).** An empty `pool.run` costs
**0.434 us at 4 threads, 0.412 at 8, 1.329 at 16** (`/tmp/ceil2.cpp`, 2000 calls,
median of 5). A 1024-token chunk issues 1743 buckets x 5 fan-outs = 8715 calls,
i.e. **11.6 ms of a ~2400 ms chunk = 0.48%**. Even eliminating every fan-out
cannot pay for a rewrite that risks races in scatter/reduction.

**Fused prefill QKV (proposed priority 5).** `pack_a_tiles` costs **0.070 ms at
m=512 and 0.133 ms at m=1024** (`/tmp/packc.cpp`), against a QKV stage of
1.053 + 2.796 ms at m=512. Three separate GEMMs pay the pack three times, so the
saving is at most **0.14 ms of a 1.61 ms stage = 8.7%**, and the QKV+o_proj stage
is ~10% of a 16k run, so **0.87% end-to-end** — inside run-to-run noise.

Recorded so neither is re-proposed on the strength of EXP-0058's fan-out remark:
that remark was about the MoE *GEMM's* internal split, which EXP-0058 already
fixed by packing inside the same worker loop.

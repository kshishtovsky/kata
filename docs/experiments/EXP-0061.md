# EXP-0061: why the q4_K VNNI tile sits at 55% of peak — instruction-level audit

Status: PASSED (diagnosis) / no code change kept

## Question

`gemm_q4_K_q8_K_mt` reaches 2695-2735 GMAC/s at n=6144, which is 54-55% of the frozen
VNNI peak (4975 GMAC/s, 16 threads). Both `-march` targets and `VRN` were already tuned.
Where do the other 45% go?

## Measurements

`perf stat` on 50 single-thread calls of `gemm_q4_K_q8_K_mt` (m=512 n=6144 k=2048):

    8.63e9 cycles   17.73e9 instructions   IPC 2.05
    306M branches   8.48e9 L1 loads       1.52e9 L1 misses

37 MAC/cycle against the 64 MAC/cycle VNNI peak. `objdump -d` on the `q4_K_vnni_tile`
body, one sub-block iteration:

    64 vpdpbusd   64 vpbroadcastd   72 vpmulld   64 vpaddd   13 vpxor

So per 8 rows x 8 groups = 64 products the kernel also emits 64 broadcasts and 136
integer epilogue ops. `vpmulld` on Zen 4 has a throughput of 1/cycle on a single port,
which is the same port family `vpdpbusd` uses for its accumulator writes.

This is arithmetic, not profiler guessing: a broadcast issued as its own instruction
means two instructions per 64 MAC, so the ceiling for this shape is 50% of the
`vpdpbusd` peak no matter how good the rest is. 55% measured is 110% of that ceiling,
i.e. the compiler already folds part of the broadcast into the load.

## Attempts, all measured, none kept

| change | m=512 result | verdict |
|---|---|---|
| baseline (VRN=8) | 2695 GMAC/s (54.2%) | reference |
| `VRN=16` | 1223 GMAC/s (24.6%) | 2.05x worse, register pressure |
| `VRN=4` | 2566 GMAC/s (51.6%) | worse |
| hoist `a16` zeroing out of the sub-block loop | - | WRONG: `a16` accumulates per sub-block; caught by `GemmQ4K.MatchesPerRowGemv` |
| drop `(int)` on `set1_epi32` | 96 broadcasts instead of 64 | worse |
| float epilogue (`vfmadd` instead of `vpmulld`) | 2637 GMAC/s (53.0%) | worse |

## Conclusion

The remaining gap is the missing `{1to16}` memory form of the weight operand: a
broadcast that feeds only one `vpdpbusd` cannot be amortised. Two real options, both
structural rather than micro:

1. One broadcast feeding two token tiles (VTN=32, VRN=4). Prototype `/tmp/v32.cpp`
   segfaulted inside its own harness and was not completed; register budget
   (VRN x VTN/16 += accumulators, s1 and a16 each again) says 4x2 = 8 accumulators
   plus 8 staging plus 8 sums is the most that fits in 32 zmm.
2. Repack weights once per layer into a layout where four rows share one zmm
   (the ggml `tiled_repack_src0` trick), turning one load into four products.

Neither is a micro-optimisation: both change the pack format. Left as an open
direction with the ceiling documented, because at 55% of peak the kernel is not the
top target in a 16k prefill profile (attention core 12878 ms and conv 4475 ms of
38341 ms total).

## Addendum: the VTN=32 / VRN=4 structure was built and measured

A standalone replica (`/tmp/v32.cpp`, single core, `taskset -c 0`, identical scale/min
packing, exact q4_K nibble order) ran both shapes over the same 6144x2048 q4_K matrix:

| shape | m=512 | m=1024 |
|---|---|---|
| VTN=32 VRN=4 (one broadcast feeds 2 products) | 36.56 ms / 176.2 GMAC/s | 73.90 ms / 174.4 |
| VTN=16 VRN=8 (current shape) | 33.30 ms / 193.4 GMAC/s | 67.18 ms / 191.8 |

Both sit at 56-62% of the 311 GMAC/s single-core peak, so the replica captures the
same effect the real kernel shows, and the wider tile is 9% SLOWER. Amortising the
broadcast over two products does not pay because the extra token tile costs a second
`codes` load, a second accumulator set and a second `s1`/`a16` staging set, all of
which the register file cannot hold at VRN=4 without spilling.

Practical consequence: at ~56% of single-core peak there is roughly 1.7x of headroom,
but every mechanism tried so far (VRN sweep, epilogue domain, broadcast amortisation)
lands on the wrong side of the register budget. The remaining untried route is the
once-per-layer weight repack where four weight rows share one zmm, which changes the
pack format rather than the loop nest.

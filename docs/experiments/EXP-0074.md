# EXP-0074 — Decode attention on the GPU at 16k

**Status:** PASSED (traffic floor measured) / NEEDS_RESEARCH (real kernel not
written)
**Hardware:** Ryzen 9 7950X3D, Radeon RX 7900 XT (gfx1100, 21.4 GB), ROCm 10.1
**Code:** `bench/bench_hip_attn.cpp`

## 1. Problem

EXP-0072/0073 put a whole decode token's weight traffic on the GPU: 1517.6 MB
in 3.72 ms (408 GB/s, 53% of the 764 GB/s read ceiling). Weights are therefore
no longer the problem if the model is resident.

But a token is not only weights. At 16k context the CPU token is 31.62 ms, of
which attention is 9.06 ms — 29%, and **ALU-bound**, not memory-bound: EXP-0066
showed a 64x change in resident footprint moved the attention rate by 7%, and
the kernel issues 0.10 zmm-FMA/cycle against Zen 4's 2.0. That is the one stage
where the GPU's balance is the opposite of the CPU's, so it decides whether the
projected 8.5x survives contact.

## 2. What was measured, and what was not

`attn_decode_kernel` in this file is **scratch, not a kernel**: it reads K and V
correctly but its online-softmax rescale line is wrong and it writes nothing
useful. Its 72.5 ms is therefore not a result and is printed only to be ignored.

What the file does answer is the floor: read K and V once per (layer, kv head)
at 16k — 336 MB — with enough blocks to fill the card. A real split-KV decode
attention cannot beat that floor, and any kernel that comes near it is
memory-limited rather than ALU-limited, which is exactly the inversion of the
CPU situation we needed to check.

## 3. Three probe bugs, all of which produced believable numbers

Each of these was caught only because the result contradicted something already
known. That is the argument for having the 764 GB/s ceiling written down.

**Bug 1 — one block per kv head.** The first version launched one 256-thread
block per (layer, kv head). It read 336 MB in 27.96 ms = **24.0 GB/s**, which
looks like "the GPU is bad at attention". It is not: a 7900 XT has 84 CUs, and
80 launches of a single block kept roughly 1% of the card busy. The kernel was
starved, not slow.

**Bug 2 — the working set fitted in cache.** Allocating one layer's K/V (67 MB)
and reusing it for all ten reported **815 GB/s against a measured 764 GB/s
ceiling** — impossible. The 80 MB Infinity Cache was serving the whole probe.

**Bug 3 — an addressing overrun.** A position is 64 floats = 16 `float4`. The
traffic kernel indexed `k4[p*16 + lane]` with `lane` up to 31, so it read two
positions per step but advanced `p` by only `nw`, skipping half of them and
running off the end of the last head. This produced the original
`Memory access fault by GPU node-1 ... Reason: Page not present`, exit 134.

## 4. Results

Grid sweep, 336 MB of distinct K/V, 10 timed reps each:

| blocks per kv head | ms | GB/s |
|---|---|---|
| 1 | 42.33 | 15.9 |
| 4 | 8.04 | 83.5 |
| 8 | 3.33 | 201.6 |
| 16 | 1.83 | 366.8 |
| 32 | 1.16 | 576.3 |
| 64 | 1.14 | 587.3 |
| 128 | 1.14 | 589.9 |
| 256 | 1.14 | 589.8 |

Plateau: **1.14 ms, 590 GB/s** (77% of the 764 GB/s read ceiling — read-only
streams land below the copy probe, consistent with EXP-0072's 603 GB/s at full
occupancy). Occupancy needs ~32 blocks per kv head; the curve is flat from there
to 256, so a real kernel should launch 64-128 and not worry about the tail.

Against the CPU's 9.06 ms that is **8.0x**, and it is the *floor*, not a
kernel — a real one adds the online-softmax merge over 8-16 partials per
(kv head, tile), which is arithmetic the GPU has spare.

## 5. Token budget on GPU at 16k

| stage | GPU | CPU |
|---|---|---|
| weights (EXP-0073) | 3.72 ms | ~19.2 ms |
| attention (this exp, floor) | 1.14 ms | 9.06 ms |
| shortconv, norms, MoE glue, samples | not yet measured | ~3.4 ms |
| **total** | **~4.9 ms → ~205 tok/s** | 31.62 ms → 31.6 tok/s |

That is **6.5x**, against the 8.5x that weights alone suggested — attention eats
0.7 of the 4.8 ms saved. It is also the first estimate in this project where the
individual terms were measured rather than modelled, so the remaining slack is
all in the unmeasured glue.

## 6. Conclusion

The GPU path is worth building. The floor is ~4.9 ms/token at 16k against a
31.6 ms CPU token, and for four concurrent agents (14.5 GB weights + 4 x 671 MB
KV = 17.2 GB) VRAM fits with 4 GB spare — which is the case the CPU cannot serve
at all, since continuous batching there tops out at 1.75x (EXP-0071).

Two things this experiment does **not** establish, and nothing should be
concluded about them yet: that a real attention kernel reaches 1.14 ms, and that
the glue (shortconv's 3-tap scan, MoE routing and gather, the sampler) ports
cheaply. EXP-0075 is the decode layer, where both get measured.

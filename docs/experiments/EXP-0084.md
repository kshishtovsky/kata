# EXP-0084 — does the resident weight stream amortise over a batch on the GPU?

**Status:** PASSED (with a compute ceiling found)
**Date:** 2026-11-27

## Problem

EXP-0083 measured one token's whole weight stream at 5 launches and 2.5-3.2 ms.
At B=1 that is a memory-bound GEMV. The GPU plan only pays for several agents if
B activation rows share the same weight bytes — the same argument that made CPU
continuous batching interesting (EXP-0071), where the answer was "yes, but the
memory floor caps it at 1.75x". Here the question is the opposite: is the kernel
still memory-bound at B>1, or does compute take over first?

## Method

`bench/hip/bench_gpu_batch.hip` takes the bulk q4_K bucket (every q4_K row one
token reads: 175 tensors, **808448 rows, 931.3 MB**, all `nb=8`), pins it in VRAM,
and runs `gemv_q4_K_batch_b<B>` with B a template parameter so the accumulators stay
in registers. Each weight block is loaded once and used B times.

Two design points that the measurement forced:

- the min term needs `sum(y)` over a group, which does not depend on the weight at
  all — `block_q8_K` already carries those sums as `bsums[16]`. Accumulating `sy`
  inside the loop cost 2 registers per activation row and pushed **B=16 into local
  memory: 458.310 ms, 2.0 GB/s** (87x slower than B=8);
- nibbles must be unpacked four at a time and spent on every activation row before
  the next word is touched, so only 8 integers are live at once.

## Result

Weights verified against `vec_dot_q4_K_q8_K_ref` first: B=1, first 2000 rows,
`max|diff| < 1e-4` relative. (The first version of this kernel reserved `int
qlo[16], qhi[16]` while writing indices 16..31 — a stack overrun that returned
**0.000000 for every row** and still ran at a reported 4560 GB/s, 6x above the
card's own ceiling. The ceiling is the only reason it was caught.)

## Conclusions

- **Amortisation is real but small: 2.55x on per-token time at B=16, and the
  curve is flattening.** Weight bandwidth falls monotonically (721 -> 115 GB/s)
  while GMAC/s climbs to a plateau at **~3270**. The kernel becomes compute-bound
  around B=4-8.
- **3270 GMAC/s is also the CPU's own VNNI rate** (EXP-0054: 3102 GMAC/s at
  n=11776). This scalar GPU kernel — one nibble multiply per instruction — is not
  faster than 16 Zen 4 cores at raw MAC throughput. All of the GPU's 8.9x on a
  single token comes from bandwidth, and bandwidth is exactly what a batch spends
  to buy compute.
- The fix is not a bigger batch, it is the instruction: gfx1100 has
  `v_dot4_i32_i8` (`__builtin_amdgcn_sdot4`), which would cut the MAC count per
  instruction ~4x and move the plateau to ~13 T MAC/s — above the point where
  B=16 is memory-bound again. That is the next experiment, and it decides whether
  a GPU backend scales to several agents or only serves one fast chat.
- Reproducibility note: clock ramp makes a cold run read ~29% slower than a warm
  one for the identical binary and identical work (3.241 vs 2.521 ms on the
  EXP-0083 token). Both figures are honest; the warm one is the steady state.

## Next

`v_dot4_i32_i8` in the bucket kernels, then re-run both this B-curve and the
EXP-0083 token. If the plateau moves as predicted, the GPU backend is worth
building; if not, the card stays a single-chat accelerator.

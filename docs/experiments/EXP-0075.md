# EXP-0075 — A real GPU decode-attention kernel at 16k

**Status:** PASSED
**Prerequisite:** EXP-0074 (traffic floor 1.14 ms at 16k)
**Code:** `bench/bench_hip_attn.cpp` (same file, second half)

## 1. Problem

EXP-0074 established that reading K and V once per (layer, kv head) at 16k costs
1.14 ms = 590 GB/s. That is a floor, not a kernel: it contains no dot products,
no softmax, no merge. A real kernel must land close to it for the GPU projection
to hold, and the CPU number it replaces is 9.06 ms.

## 2. Hypothesis

If the kernel is arranged so that one loaded key serves all four q heads of a
GQA group, and the cross-lane reductions happen once per tile of positions
rather than once per score, the kernel should be memory-bound and land near
1.14 ms. If instead each warp handles one q head, the keys are read four times
and the kernel becomes a 4x traffic multiplier.

## 3. Implementation

Grid `(nblk, kKvHeads)`, 128 threads per block = 4 warps. Warps split
**positions**, not q heads; each warp carries all four q heads of its group, so
`k2` and `v2` serve four dots and four accumulators. Lane `i` owns dims
`(2i, 2i+1)`, so a score is a 2-FMA dot plus a 5-step `__shfl_xor_sync` and the
softmax denominator is one more 5-step fold. Partials are `(m, l, acc[4][64])`
per (block, warp, kv head); `attn_merge` combines `npart` of them per q head in
524288 floats of total traffic.

## 4. Results

Accuracy against `kata::attention_decode_grouped` on the same data:
**max|abs| 3.5e-08** on outputs up to 0.0072.

| blocks per kv head | ms | GB/s | vs CPU 9.06 ms |
|---|---|---|---|
| 8 | 4.37 | 153.5 | 2.1x |
| 16 | 2.34 | 287.0 | 3.9x |
| 24 | 1.70 | 393.8 | 5.3x |
| 32 | 1.41 | 477.3 | 6.4x |
| **64** | **1.34** | **500.3** | **6.8x** |
| 128 | 2.00 | 336.3 | 4.5x |
| floor | 1.14 | 590.0 | 8.0x |

The optimum is **64 blocks per kv head**; the kernel reaches 83% of the floor.
Past 64 it degrades — the per-block position tile shrinks below the point where
the K/V stream amortises the fixed per-block cost, and the merge grows.

## 5. Two failed variants, and what they taught

**Warp per q head** (the natural arrangement): correct at 3.4e-08, but 1.95 ms.
All four warps walked the same tile, so K and V were read four times. The
correction — one warp carries the whole group and pays 4x the shuffles — is
counter-intuitive on a card with spare ALU, and the measurement is what settled
it: traffic, not arithmetic, was the constraint even with 20 shuffles per
position in the way.

**One lane per position**: bit-identical to the CPU kernel (`max|abs| 0.000e+00`
— the only variant that was), because it needs no cross-lane reduction at all.
It ran **5.89 ms**, 4.4x slower. One lane reading 16 `float4` of a position
serialises the entire 256-byte line through a single lane's load path; with 32
lanes per position the accesses coalesce into one transaction. Bit-identity cost
4x here and bought nothing measurable, which is the same conclusion EXP-0043
reached on CPU from the other direction.

## 6. Token budget at 16k, all terms now measured

| stage | GPU | CPU |
|---|---|---|
| weights (EXP-0073) | 3.72 ms | ~19.2 ms |
| attention (this exp) | 1.34 ms | 9.06 ms |
| shortconv + norms + MoE glue + sampler | not yet measured | ~3.4 ms |
| **measured subtotal** | **5.06 ms → 198 tok/s** | 31.62 ms → 31.6 tok/s |

**6.3x** on the measured stages. The 8.5x that weights alone suggested is gone:
attention and the glue that has not been ported yet account for the difference,
and attention is now at 83% of a hard floor rather than an open question.

## 7. Conclusion

Keep. The kernel is correct, lands at 83% of the measured floor, and its block
count is settled by a sweep rather than guessed. The GPU token at 16k is
5.06 ms of measured stages against a 31.62 ms CPU token, so EXP-0076 (port the
glue, assemble a whole decode layer) is the next step and the last unknown in
the projection.

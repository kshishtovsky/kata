# EXP-0056 — blocked QK+PV prefill (flash shape): FAILED, 0.87x

Status: FAILED (reverted)
Date: 2026-11-27

## Hypothesis

Prefill attention reads K once per query row. Blocking by query rows lets a
block share one transposed K tile, cutting K traffic proportionally to the
block size: at a 32k prefix, 16 rows/block takes 68.7 GB per 1024-token chunk
down to 4.29 GB, and 32 rows/block to 2.15 GB, while the block's accumulator
(16 rows x 4 heads x 64 dim = 16 KB) stays in L1. Expected: 1.2-1.4x on the
attention core, which is 42% of a 32k prefill.

Arithmetic done before writing code, on the block and not on the whole batch
(the earlier rejection of ADR 0001 was wrong precisely because it used the batch).

## Implementation

`prefill_group4_blocked` in `/home/medovarov/kata/src/prefill.cpp`: positions
in lanes (16 per tile), a query block of `q_tile` rows, transposed K tile built
into 4 KB of L1 scratch once per (tile, block), online softmax per (row, head),
V read position-major. `KATA_QTILE` selects the block size; 1 falls back to the
existing row-at-a-time kernel.

Two real bugs found while building it, both worth recording:

1. `std::vector<__m512>` is malloc-aligned, not 64-byte aligned, so the first
   `_mm512_load_ps` on it segfaulted. Fixed with an `AlignedF32<__m512>`
   allocator over `std::aligned_alloc(64, ...)`.
2. The causal bound used `break` where it had to use `continue`: `lim` grows
   with the row index, so an early row skipping a tile does not mean a later
   row in the same block skips it. `Prefill.MtSplitMatchesSingleThreaded`
   caught it; `Prefill.MatchesRefAcrossShapes` did not, because at small
   `n_tok` the rows that would have been skipped happened to be clipped anyway.

## Measurement

| config | 8k prefill | 16k prefill |
|---|---|---|
| baseline (`q_tile = 1`) | **502.4 tok/s** | 399-403 tok/s |
| blocked, q_tile 16 | 436.0 | 342.0 |
| blocked, q_tile 32 | 440.3 | 348.5 |
| blocked, q_tile 64 | — | 345.8 |

**0.87x on 8k, 0.86x on 16k — a consistent slowdown, and the logit moved from
28.45286 to 28.01776.**

## Why it failed — the model was wrong again, in the same direction

MAC and FMA counts are identical between the two forms:

- blocked: 256 FMA per (row, tile), each 16 MAC wide
- original: 16 positions x 4 heads x 4 FMA = 256 FMA per (row, tile)

So blocking changes bytes read, not instructions issued. The traffic bound that
justified it was computed for the wrong working unit: at 16k the K traffic floor
is 0.45 s per chunk against 1.64-1.72 s measured, i.e. the kernel runs **2.3x
above its traffic floor**. It is ALU-bound, so removing bytes removes work that
was already overlapped with arithmetic, and the blocked form *adds* 1024 stores
per tile for the transpose plus 16 KB of accumulator traffic.

The traffic reduction is real (68.7 GB -> 4.29 GB at 32k, 16x) but it is not
the binding constraint at the depths that matter.

## Conclusion

REJECTED, reverted with `git checkout src/prefill.cpp`. The 2.14x score-pass
microbenchmark keeps its meaning — it is a per-row kernel win that this engine
cannot collect, because per-row traffic was never the bottleneck here.

The only remaining levers on the attention core are arithmetic ones: fewer
instructions per MAC (int8 `vpdpbusd` at 311 vs 165 GMAC/s peak) or fusing PV
into the same pass. Both change numerics and need a PPL gate.

## Rule adopted

Compute a ceiling on the smallest real working unit the kernel actually runs on
— one row, one tile, one block — not on the whole batch. Both the false 64x and
this false 16x came from getting that unit wrong in opposite directions.

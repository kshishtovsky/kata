# EXP-0063: the weight repack is a non-problem, and the epilogue is not the loss

Status: REJECTED (three variants measured, all reverted)

## Why this was opened

EXP-0061 read `objdump` and concluded the tile runs at 50% of the VNNI peak
because of one `vpbroadcastd` per `vpdpbusd`, and proposed repacking every
weight band once per layer so four rows could share a zmm. A reviewer pass
read `gemm.cpp:405-416` and refuted the premise: `q4_K_vnni_rows` already
unpacks each band once and runs **all** token tiles against it, and workers
take disjoint row windows, so there is no duplication to remove. The reviewer
put the removable share at ~0.7% of prefill (m=512, ntile=32) and the register
budget at 24 of 32 live zmm, not 32.

I verified that reading myself against the loop structure and agree.

## Measurement 1: the broadcast is worth 2%, not 50%

`/tmp/ceil.cpp` runs the exact inner-loop shape (8 rows x 8 sub-blocks x 8
groups, one `codes` load per group) in two arms with identical MAC counts:

| arm | instructions per product | time | GMAC/s |
|---|---|---|---|
| A `set1_epi32` + `dpbusd` (shipped) | 2 | 24.246 / 24.291 / 24.386 ms | 270.3 |
| B `dpbusd m32bcst` | 1 | 23.783 / 23.889 / 23.770 ms | 275.6 |

+2.0%. The single-core VNNI peak is 311 GMAC/s, so the isolated loop already
runs at **87% of peak** and the broadcast is nearly free. EXP-0061's 50%
arithmetic argument counted instructions without counting issue width.

## Measurement 2: replacing `vpmulld` with cvt+fma loses

Hypothesis: `vpmulld` is the slowest int op in the loop (2 uops, 1/cycle on
Zen 4) while `vfmadd` issues 2/cycle, so converting `a16` and the sub-block
scale to float should win. `a16 <= 61k` and `sc <= 63` fit float32 exactly,
so only the sum over 8 sub-blocks rounds.

| | m=256 | m=512 | m=1024 |
|---|---|---|---|
| baseline | 2242.9 (45.1%) | 2714.6 (54.6%) | 2687.1 (54.0%) |
| float epilogue | 2359.0 (47.4%) | 2623.0 (52.7%) | 2665.5 (53.6%) |

Wash at best, worse at m=512/1024. Reverted. `Gemm*` tests passed both ways,
so this was a pure performance verdict.

## What this leaves

The isolated inner loop reaches 87% of peak; the shipped kernel reaches 54%.
The 33-point difference is everything around the loop: the separate `s2` pass
over all sub-blocks, the `d`/`dmin` epilogue, the `dact` broadcast, the tile
store. Both attempts to shrink that staging halved or hurt. The next honest
step on this kernel is to fold the `s2` (min) pass into the main loop so `bsum`
is consumed while the band is hot, not to repack weights.

The reviewer's caveat is recorded: at `ntile` 1-2 (small-m decode with
`n >= nt`) the unpack share rises to 18-37%, so the calculus does change if
that path ever becomes hot.

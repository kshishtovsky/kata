# EXP-0072 — q4_K GEMV on the GPU, checked against the CPU kernel

**Status:** PASSED (correctness) / PARTIAL (throughput)
**Date:** 2026-11-27

## 1. Problem

The RX 7900 XT has been idle since the project started by user decision. A
read-only probe (EXP-0071) measured 764.3 GB/s against the CPU's 73.5 GB/s, so
the obvious question is whether a real kernel — not a probe — can capture that
on the format the shipped models actually use.

Before any GPU backend work the correctness question has to be answered first:
does a HIP kernel reading the same q4_K blocks produce the same numbers as the
CPU path? If not, everything downstream is built on sand.

## 2. Hypothesis

A q4_K GEMV on the GPU should land within 2x of the 764 GB/s read ceiling, and
should agree with the scalar CPU reference to better than 1e-4 relative.

## 3. Implementation

`bench/bench_hip_gemv.cpp`, built with `hipcc` by hand (not in the CMake build).

Kernel design, one 4-thread group per q4_K super-block:

- Each thread owns **one 32-byte group of `qs`**, which holds two sub-blocks at
  once: `qs[32i+l]` is value `32i+l` in the low nibble and `32i+32+l` in the
  high nibble. So one 32-byte read feeds two 32-value sub-blocks.
- 64 groups per 256-thread block, so a block covers either several whole rows
  (`nb <= 64`; real case is `cols = 2048` → `nb = 8`, i.e. 8 rows per block) or
  a slice of one row. Both reduce inside the block: no atomics, no cross-block
  partials, deterministic and directly comparable with the CPU.
- `f16` conversion is done by bit pattern on device. `__ushort_as_half` is not
  available without pulling a header, and the CPU path already needed a subnormal
  bugfix (EXP-0006), so the device path is verified explicitly against
  `kata::f16_to_f32` over subnormals, zero, and the max.

## 4. Bugs found

1. **Reduction dropped 3 of every 4 group sums.** With 4 groups per warp, only
   the warp leader published a partial, so 24 of 32 super-blocks never
   contributed. Relative error 4.7e+03. Caught because the gate was absolute.
2. **Two lanes read the same 32 bytes.** The first version used 8 threads per
   super-block, one per 32-value sub-block, so both nibble halves were loaded
   twice. Restructuring to 4 threads (one per byte group, both nibbles) took
   the tensor from 153.5 → 253.7 GB/s with no change to the arithmetic.
3. **`__shfl_down_sync` mask must be 64-bit** on gfx1100; a 32-bit mask is a
   hard compile error, not a warning.
4. **Best-of-N per tensor reported 2485 GB/s against a 764 ceiling.** A 13.6 MB
   tensor fits in the 80 MB Infinity Cache, so reps 2..N were cache hits. The
   sweep now rotates its start offset across reps and times the whole sweep.

## 5. Results

Accuracy versus `kata::vec_dot_q4_K_q8_K_ref` on `blk.0.ffn_gate.weight`
(11776×2048, 13.6 MB):

```
accuracy: max|abs| 1.431e-06  largest |row| 3.453  tol 3.453e-04 -> OK
```

Correct, with the expected float-summation-order difference and nothing else.

Single tensor, resident in VRAM, best of 20:

| | ms | GB/s | vs ceiling |
|---|---|---|---|
| GPU q4_K GEMV | 0.053 | 253.7 | 33% |
| CPU, 1 thread, scalar ref | 3.3 | — | 61x slower |

**One decode token's worth of q4_K weights**, single timed sweep over every
tensor (4 of 64 experts, which is what a token activates):

```
195 tensors, 1072.9 MB, 2.81 ms -> 381.4 GB/s (50% of ceiling)
```

For scale, all 64 experts (not what a token reads): 11265 MB, 18.66 ms,
603.5 GB/s — 79% of ceiling, so the kernel does reach the hardware once the
working set is large enough to defeat the cache.

Launch overhead, measured with an empty kernel: **2.77 us per launch**, and 195
launches is 0.54 ms — 19% of the 2.81 ms sweep. A CUDA/HIP graph replay was
measured and gives 2.83 us/node, i.e. **no improvement on this driver**, so
batching commands is not a lever here.

## 6. Extrapolation, and its limits

q4_K is 70% of decode traffic (1072.9 of 1538.9 MB). If the q6_K and f16
remainder streamed at the same measured rate, a token costs ~4.03 ms =
**~248 tok/s**, against 31.6 tok/s on CPU at 16k depth — **7.8x**.

This is a projection, not a measurement. What it assumes and does not prove:

- q6_K has no GPU kernel yet. It is 16 sub-blocks of 16 values vs q4_K's 8 of
  32, so the epilogue doubles — the same trap that made its CPU VNNI version
  fail at 0.61x before EXP-0029.
- 4-of-64 experts here are the *contiguous* first four slabs. Real routing picks
  arbitrary expert ids; bandwidth should be similar but it is unmeasured.
- Attention, MoE routing, KV cache, sampling, and the residual stream are all
  absent. They are small in bytes but not necessarily in time.
- 195 launches at 2.77 us is 19% overhead and graphs do not remove it.

## 7. Conclusion

The GPU path is real: the kernel is numerically correct, reaches 50% of the
read ceiling on a decode-shaped sweep and 79% on a cold one. A 7.8x decode
projection is worth chasing, and it is the only lever of that size left — CPU
continuous batching was bounded at 1.75x in EXP-0071.

Next: **EXP-0073 — q6_K on the GPU**, because q6_K is the remaining 30% and it
is the format most likely to break the pattern (EXP-0026 already showed it
failing on VNNI for a structural reason).

# EXP-0082 — do the CPU and the GPU share bandwidth, and what does a token's MoE cost on the GPU?

**Status:** PASSED
**Date:** 2026-11-27

## Problem

EXP-0080/0081 priced a hybrid decode at 2.3x (8 GB) with 28 us of handoff tax per
layer. Both rest on an unmeasured assumption: that the CPU's share and the GPU's
share run **concurrently**, so a layer costs `max(cpu_i, gpu_i)`.

That is only true if the two devices' bandwidths are independent. They are not
obviously so — the GPU reads its weights over PCIe through the host memory
controller, so it could steal the very bandwidth the CPU's shares need. If it
does, the `max()` collapses to a `sum()` and the whole hybrid plan loses its
premise.

`bench/hip/bench_hybrid.hip` measures it, and `bench/hip/bench_moe_gpu.hip` then
prices what the hybrid actually buys.

## Method

`bench/hip/bench_hybrid.hip` (`hipcc -O3 bench/hip/bench_hybrid.hip -o /tmp/hyb
-I include -L build -lkata_core -lpthread`):

- all 64 `blk.2.ffn_gate_exps` slabs (113.2 MB) staged in VRAM, activation row in
  VRAM, one fused `gemv_q4_K_batch` launch over `nslab` slabs on a **flat 1-D**
  grid;
- the CPU arm runs the same bytes through `gemv_q4_K_q8_K_mt` on the 16-thread pool;
- split arms run both at once and compare against the serial sum.

`/tmp/contend2.hip`, `/tmp/contend3.hip` isolate contention: an L3-resident
`gemv` (8 experts, 14 MB) and a DRAM-bound one (64 experts, 113 MB), each with the
GPU streaming 1 GiB in a background thread, with the CPU clock sampled from
`/proc/cpuinfo` during each condition.

`bench/hip/bench_moe_gpu.hip` concatenates **one token's entire expert footprint**
— 38 MoE layers x 4 experts x 6.1 MB = 930 MB — into one blob, uploads it, and runs
the token's MoE stage (114 launches: gate, up, down per layer) against it.

## Results

### Contention — there is none

| CPU arm | alone | with GPU streaming 1 GiB |
|---|---|---|
| L3-resident (8 experts) | 0.092 ms | 0.103 ms (1.11x) |
| DRAM-bound (64 experts) | 0.883 ms | 0.813 ms (0.92x) |

Clock: idle 3781 MHz, 3952→4086 MHz during CPU-only work, 3099→4164 MHz with the
GPU busy. The first attempt reported a 3.93x slowdown; that was an artifact — the
CPU arm was 0.048 ms long, too short to sample anything, and the GPU busy loop
held a thread.

### Concurrency — the bandwidths add up

Whole layer, 64 experts, 113.2 MB, 16 threads:

| arm | ms | GB/s |
|---|---|---|
| CPU only | 1.02–1.13 | 100–111 (L3-warm, above the 73.5 DRAM ceiling) |
| GPU only | 0.422 | **268.1** |
| 44 GPU + 20 CPU, concurrent | 0.162 vs 0.284 serial | **1.75–1.77x** |
| 32 + 32 | 0.221 vs 0.331 | 1.48x |
| 16 + 48 | 0.341 vs 0.414 | 1.21x |
| 54 + 10 | 0.225 vs 0.249 | 1.11x |

### Real decode shape — splitting a layer is a loss

4 experts per layer = 7.1 MB, which fits L3:

| cpu:gpu | concurrent | vs CPU only |
|---|---|---|
| 4:0 | 0.023 ms | 1.00x |
| 3:1 | 0.044 ms | 0.52x |
| 2:2 | 0.045 ms | 0.50x |
| 1:3 | 0.044 ms | 0.52x |

One GPU launch plus handoff is ~25–30 us; the CPU does the whole 7 MB slab in
23 us. This is the wall EXP-0012 and EXP-0064 hit — **latency per operation, not
bandwidth**.

### The whole token's MoE, resident on the GPU

Verified against the CPU reference first: **max|diff| 9.537e-07 on a 2.871 scale
= 3.3e-07 relative**, PASS.

| | value |
|---|---|
| footprint | 930 MB uploaded once, 61 ms at 15.3 GB/s |
| MoE per token | **1.690 ms** (114 launches, 0.32 ms of it launch overhead) |
| payload | 1.374 ms = **676.9 GB/s (88.6% of the 764 ceiling)** |
| CPU engine `ffn` | 14.20 ms |
| **speedup on the stage** | **8.40x** |
| projected token | 22.5 − 14.20 + 1.69 = **9.99 ms = 100 tok/s** |

## Traps found

1. **Zero-copy is wrong for anything a kernel reads per block.** A mapped host
   activation row made 2.3 KB of setup into megabytes of PCIe traffic across
   12288 blocks: **61.3 GB/s vs 268.1 GB/s**. Zero-copy is right for the 2 KB
   handoff payload (EXP-0081) and wrong here.
2. **A 2-D grid made each slab its own wavefront**: 60.3 GB/s against 268 on a
   flat 1-D grid.
3. `std::vector<block_q8_K> hx(nb)` was written as one block for a 2048-wide row;
   the quantiser overran the stack and the crash surfaced as a SIGSEGV in
   `GgufFile::~GgufFile()` — three runs lost to a misread stack trace.
4. `hipHostMalloc` for a mapped row must cover whole pages (+4096), not 292 bytes.
5. `vec_dot_q4_K_q8_K_ref` takes a **value count**, not a block count; passing
   `nb` made the reference read `1/8` of each row and the verification FAIL with
   a plausible-looking 2.871 max|diff|.
6. A per-rep timing multiplied by `reps` in the launch-overhead subtraction
   reported **11503 GB/s** — above the card's own measured 764 ceiling, which is
   the only reason it was caught.

## Conclusion

- The hybrid's premise holds: **CPU and GPU bandwidth are independent** (no
  DRAM contention at all), and concurrent split reaches 1.75x on a cold layer.
- **Per-layer splitting of a 4-expert MoE is not viable**: the CPU finishes 7 MB
  in 23 us, so any GPU participation costs more in handoff than it saves.
- **Whole-footprint residency is decisively viable**: with a token's 930 MB of
  experts resident, the GPU runs the MoE stage in 1.69 ms at 89% of the memory
  ceiling, **8.4x the CPU's 14.20 ms**, and the token lands at 9.99 ms = 100 tok/s.
- The two findings together say the hybrid must be built as **residency**, not as
  splitting. That is the same conclusion EXP-0078's curve pointed at, and this
  time it rests on a measurement rather than a traffic model.
- 930 MB of resident experts is a third of the 24B model's expert set and fits
  comfortably in 20 GB VRAM alongside 14.5 GB of weights only if the KV cache and
  attention also move — which EXP-0081 priced at 28 us/layer.

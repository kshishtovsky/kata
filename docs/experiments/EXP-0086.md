# EXP-0086 — the MoE stage as a real pipeline: launches and transfers counted

**Status:** PASSED (the pipeline holds at 83.6 tok/s, but two of the three costs
are launch and handoff, not arithmetic)
**Date:** 2026-11-27

## Problem

EXP-0082 measured the token's whole expert footprint at **1.690 ms** with the
activations already on the device, one activation row shared by all four experts,
and three launches per layer. None of those three conditions holds in a real
decode:

1. the four experts of a layer sit **6.1 MB apart** inside a stacked tensor, so a
   single launch cannot cover them without a gather;
2. the down projection consumes `silu(gate)*up`, which is a *different* row per
   expert — that work and its requantisation have to happen somewhere;
3. the router runs on the CPU, so the residual stream crosses PCIe at least once
   per layer in each direction.

EXP-0081 priced the handoff at ~20 us and, at 38 layers, that is 1.5 ms — the
same order as the 1.7 ms of arithmetic being moved. So the number that decides
whether a GPU MoE is worth building is not 1.7 ms, it is the whole loop.

## Method

`bench/hip/bench_moe_gpu.hip`, extended with two arms over the same resident
weights and the same activation row (all verified against the CPU reference first):

- **A — grouped, no transfer.** 3 launches per layer covering all four slabs, as
  EXP-0082 measured.
- **B — per expert, no transfer.** 12 launches per layer, one per expert matrix,
  which is what a stacked tensor layout forces.
- **C — per expert + per-layer handoff.** As B plus one H2D of the q8_K row and
  one D2H of 4x2048 floats per layer, synchronous, through pinned buffers.

The down projection still shares one activation row in B and C. With per-expert
activations it would read four rows instead of one — 1.2 KB of a 6.1 MB slab —
which cannot move the result.

Model: all 38 MoE layers of `LFM2.5-24B-A2B-Q4_K_M.gguf`, **0.93 GB resident**
(the four selected experts per layer, not all 13.8 GB of experts).

## Result

Verification (gate bucket, same weights and activations as the CPU reference):
`max|abs| 9.537e-07 on scale 2.871` = **3.3e-07 relative, PASS**.

| arm | ms/token | delta | attribution |
|---|---|---|---|
| A grouped, no transfer | 1.717 | — | 541.8 GB/s, launches 0.32 ms |
| B per expert | 2.806 | +1.089 | **2.4 us x 456 launches** |
| C + H2D/D2H per layer | 3.663 | +0.857 | **22.5 us x 38 layers** |

Whole token, replacing the CPU's `ffn` 14.20 ms with C:

```
22.50 - 14.20 + 3.663 = 11.96 ms  ->  83.6 tok/s   (vs 43.9 today, 1.90x)
```

## Analysis

- **The arithmetic is only 47% of the pipeline.** 1.72 ms of 3.66 ms. The other
  53% is 456 kernel launches (1.09 ms) and 38 pinned handoffs (0.86 ms), neither
  of which any earlier experiment charged.
- **Launch cost is 2.4 us, not 2.77 us** — measured here as the slope of the
  delta over 456 launches, and below the empty-kernel figure because the launches
  overlap the previous kernel's tail. Extrapolating a per-launch constant from an
  empty kernel would have overestimated this arm by 15%.
- **Bucketing recovers most of the launch cost.** EXP-0083 got five launches for
  the whole weight stream by transposing every selected slab into one contiguous
  blob. The same trick applies here: gather the four experts of a layer into one
  staging buffer at startup. It trades VRAM (a second copy of the resident set)
  for ~1.0 ms of a 3.66 ms stage, so it is the next thing to measure, not an
  assumption to bake in.
- **The handoff is 22.5 us, matching EXP-0081's 20 us prediction.** That validates
  the projection independently, and it means the 0.86 ms is a floor set by the
  CPU router sitting inside the loop — not by PCIe bandwidth (32 KB at 16 GB/s is
  a rounding error). The only way to remove it is to move the router to the GPU,
  which is a different experiment.
- The honest end-to-end win is **1.90x**, not the 8.27x the arithmetic alone
  suggests. As with every other projection in this project, each unmeasured term
  shrank the number: 8.5x -> 6.3x -> 5.3x for the token (EXP-0076), 5x -> 1.3-1.5x
  for GPU batching (EXP-0085), and now 8.27x -> 1.90x here.

## Traps

- The `dout` buffer for arm B must be sized for one expert matrix, not for four:
  the per-expert kernels write `rows` floats each and reuse the same output slot.
  Sharing one slot is deliberate — the arm is measuring launch cost, and a
  distinct slot per expert would add an unused 49 KB of writes.
- Pinned buffers are allocated with `hipHostMalloc` and freed with `hipHostFree`;
  freeing a plain `malloc` buffer as host memory faults.
- `hipHostFree` is `nodiscard` in ROCm 7.16 and fails the build under `-Werror`
  style review; cast to void.

## Conclusion

Keep. The GPU MoE pipeline is **1.90x** on the whole token with weights resident,
and the two dominant costs (launches, handoff) are both addressable without
touching the arithmetic: expert staging kills most of the launch cost, and a
device-side router kills the handoff. Both are measured next, not assumed.

# EXP-0087 — pointer-array launches and a device-side combine

**Status:** PASSED (3.669 -> 2.411 ms; token 93.4 tok/s, 2.13x the CPU's MoE)
**Date:** 2026-11-27

## Problem

EXP-0086 showed the GPU MoE pipeline costs 3.669 ms of which only 1.72 ms is
arithmetic: 456 launches cost 1.09 ms and 38 pinned handoffs cost 0.90 ms. Both
were left as "addressable, measure next".

## Method

`bench/hip/bench_moe_gpu.hip`, arm D. Two fixes, neither of which needs a second
copy of the weights (unlike the staging idea floated in EXP-0086):

- **launches** — `gemv_q4_K_ptrs` / `gemv_q6_K_ptrs` take a **device array of slab
  pointers** instead of `w + slab * rows * nb`, so one launch covers all four
  experts: 3 launches per layer instead of 12.
- **handoff** — `weighted_sum` sums the four expert outputs with their router
  weights on the device, so the D2H payload is 8 KB per layer instead of 32 KB
  and there is still exactly one wait per layer.

The four down outputs in this arm are four responses to the same activation row
(all arms share it, see EXP-0086), so the weighted sum measures cost, not routing
correctness. The router still runs on the CPU here.

## Result

Correctness first: the pointer kernel is **bit-identical** to the slab kernel it
replaces (`max|diff| 0.000e+00` on a 2.858e+10 scale) — same arithmetic, only the
base pointer changed, so anything else would be a bug.

| arm | ms/token | launches | D2H/layer |
|---|---|---|---|
| A grouped (EXP-0082 shape) | 1.796 | 114 | none |
| B per expert | 2.762 | 456 | none |
| C + handoff | 3.669 | 456 | 32 KB |
| **D pointers + device combine** | **2.411** | **152** | **8 KB** |

```
token: 22.50 - 14.20 + 2.411 = 10.71 ms = 93.4 tok/s   (vs 43.9 today, 2.13x)
arm D vs arm C: 1.52x
```

## Analysis

- **D beats B** (2.411 vs 2.762) even though B has no transfers at all: 304 fewer
  launches is worth more than 38 round trips. Launch count is the dominant cost,
  not transfer volume — the same conclusion EXP-0077 reached for the weight
  stream (221 -> 5 launches bought 1.66x).
- **The pointer array must be per layer.** Handing the kernel `dgate + l` indexes
  `wptrs[slab]` with `slab` in `[0, n_used)`, so the base must already be offset
  by `l * n_used`; passing a bare layer base reads the next layer's experts. This
  was written wrong first and is the kind of defect that runs at full speed with
  no error, which is why the bit-identity check against the slab kernel exists.
- **What is left** is 0.62 ms of per-layer round trip (38 syncs) plus 0.38 ms of
  residual launch cost. The round trip cannot be removed while the router runs on
  the host: layer *i*'s experts need a decision made from layer *i*'s residual.

## Traps

- A bit-identity gate is the right test for a pointer-refactor and the wrong test
  for a new kernel: identical arithmetic must give identical bits, so any
  tolerance would hide a wrong slab pointer.
- `hipHostFree` is `nodiscard` in ROCm 7.16 — `(void)` it.
- The pointer array must be uploaded once, not per launch; re-uploading inside
  the timed loop would attribute PCIe traffic to the kernel.

## Conclusion

Keep. The MoE stage is 2.411 ms at 2.13x the CPU's, with the remaining cost
concentrated in one place: the host router inside the layer loop. That is the next
experiment, and it is also the decision point — a device router makes the whole
chain device-resident and removes the round trip entirely, at which point this
hybrid shape stops mattering and the engine should just run the token on the GPU.

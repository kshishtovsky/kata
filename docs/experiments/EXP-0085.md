# EXP-0085 — can `v_dot4_i32_i8` move the compute ceiling?

**Status:** FAILED (the instruction is fast, the kernel does not benefit)
**Date:** 2026-11-27

## Problem

EXP-0084 found the GPU bucket kernel compute-bound from B≈4, plateauing at
**3270 GMAC/s** — the same rate 16 Zen 4 cores reach with VNNI. gfx1100 has
`v_dot4_i32_i8`, four signed-byte MACs per instruction, so a 4x jump to ~13 T MAC/s
looked like the obvious fix. q4_K's nibbles are 0..15 and fit in i8, so
`lo = word & 0x0f0f0f0f`, `hi = (word >> 4) & 0x0f0f0f0f` turn one weight word into
two packed int8 groups of four.

## Method

1. **Isolated ALU throughput** (`/tmp/sdp.hip`): the same loop with `sdot4` vs a
   scalar `imad` chain, no memory traffic, 672 and 2688 blocks.
2. `gemv_q4_K_batch_sdot<B>` in `bench/hip/bench_gpu_batch.hip`, verified against
   `vec_dot_q4_K_q8_K_ref` before timing, then run through the same B sweep as the
   scalar kernel.

## Result

Isolated ALU throughput:

| kernel | blocks | GMAC/s |
|---|---|---|
| `v_dot4_i32_i8` | 672 | 10821 |
| scalar imad | 672 | 2620 |
| `v_dot4_i32_i8` | 2688 | **12151** |
| scalar imad | 2688 | 3338 |

In the real kernel (931 MB bucket, verified 3.6e-07 rel):

| B | scalar ms | scalar GMAC/s | sdot ms | sdot GMAC/s |
|---|---|---|---|---|
| 1 | 1.280 | 1293 | 1.855 | 893 (0.69x) |
| 2 | 1.742 | 1901 | 2.124 | 1559 (1.21x) |
| 4 | 2.867 | 2310 | 2.874 | 2305 (1.00x) |
| 8 | 4.366 | 3034 | **3.826** | **3462 (1.12x)** |
| 16 | 7.997 | 3313 | 12.957 | 2045 (0.52x) |

## Conclusions

- **The instruction is 3.6x the scalar rate in isolation and buys 1.12x at B=8.**
  The gap is the arithmetic-intensity of the surrounding work: at B=1 the kernel is
  memory-bound (727 GB/s, 95% of the 764 ceiling), so a faster MAC changes nothing;
  at B=8 compute finally matters and sdot4 wins; at B=16 the `y0w[B][8]` staging
  (needed to feed 128-bit loads to 4-byte dot products) exceeds the register file
  and the kernel collapses to 72 GB/s.
- **The first sdot version was 2.3x slower at B=1 (491 vs 722 GB/s) and the cause
  was not the instruction**: it replaced an auto-vectorised byte loop with eight
  separate 4-byte loads per group. Two `uint4` loads per row fixed it.
- Practical conclusion: **the operating point is B≈8, and it is bandwidth-bound
  there too** (243 GB/s against 764 — the batch's L2 footprint, not the MAC unit).
  Larger batches do not help, so a GPU backend serves up to ~8 concurrent sequences
  and the lever is footprint, not arithmetic.
- Whole-token projection from the measured per-bucket rates (EXP-0083's stream at
  the B=8 per-token efficiency of 2.68x): **~0.94 ms of weights per token**, i.e.
  1063 tok/s aggregate at B=8 = **133 tok/s per agent**, against the CPU's 31.6.
  Labelled a projection: it scales each bucket by the bulk bucket's B=8 ratio.

## Next

The backend. Five experiments have now converged on the same shape — 1.34 ms of
attention (EXP-0074), 0.90 of glue (EXP-0076), 2.5 ms of weights (EXP-0083), and
bandwidth as the only binding constraint at B=1 and B=8 alike.

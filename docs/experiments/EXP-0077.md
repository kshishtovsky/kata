# EXP-0077 — One launch per bucket: the weight stream reaches 88% of ceiling

**Status:** PASSED
**Code:** `bench/bench_hip_fused.cpp`
**Baseline:** EXP-0073 (221 launches, 3.72 ms, 408 GB/s)

## 1. Problem

EXP-0073 streams a token's weights in **221 launches at 408 GB/s** against a
764 GB/s ceiling. 221 x 2.77 us = 0.61 ms of the 3.72 ms is pure launch cost,
so removing the launches would reach 488 GB/s. That is still 36% short of the
ceiling, which raises the question the launch accounting cannot answer: are the
small tensors launch-bound, or occupancy-bound?

## 2. Implementation

A bucket table maps a global row index to an absolute row in a concatenated
blob, so `blockIdx.x` selects rows from *any* tensor in the bucket. Buckets are
keyed on **(format, nb)** — not format alone — because the kernel derives
rows-per-block from `nb` (`64/nb` for q4_K with 4 lanes per super-block, `32/nb`
for q6_K with 8), so the grid size and the kernel's own mapping must be computed
from the same rule.

That detail is where the whole experiment failed twice. The first version sized
the grid with a bucket-wide `rpb = 8` while an `nb=46` tensor's real `rpb` is 1,
so 8x too many blocks ran and `out[]` was overrun: `Memory access fault by GPU
node-1 ... Reason: Page not present or supervisor privilege`. The second
version was still wrong at `nb=46` for a subtler reason: the reduction loop ran
`for (i = 0; i < nb; ++i) s += gsum6[rr*nb + i]`, but `gsum6` has only 32 slots
— when `nb > 32` each group already covers several super-blocks, so the group
count stays at 32 and the loop must read 32 entries, not 46. It summed 14
uninitialised values and produced `inf` on 3779 of 4096 rows. Note that `nb=46`
is exactly the case no single per-tensor benchmark ever exercised (EXP-0073's
down tensor was the only one and it was checked against a per-tensor kernel that
had the identical bug).

## 3. Results

All **1,254,400 rows** verified against `vec_dot_q4_K_q8_K_ref` /
`vec_dot_q6_K_q8_K_ref`: `max|abs| 4.530e-06`, zero rows outside 1e-4.

| bucket | rows | ms |
|---|---|---|
| q4_K nb=8 | 808448 | — |
| q4_K nb=6 | 163840 | — |
| q6_K nb=8 | 130560 | — |
| q6_K nb=6 | 147456 | — |
| q6_K nb=46 | 4096 | — |
| **5 launches, total** | **1254400** | **2.241 ms → 677.3 GB/s** |

**88.6% of the 764 GB/s ceiling**, against 408 GB/s per-tensor: **1.66x** on the
weight stream, which is *more* than the 0.61 ms of launch cost predicted. So the
small tensors were both launch-bound and occupancy-bound, and one launch per
bucket fixed both — each block now has hundreds of thousands of rows to draw
from instead of one tensor's worth.

## 4. Token budget at 16k, every term measured

| stage | before fusion | fused |
|---|---|---|
| weights | 3.72 | **2.24** |
| attention (EXP-0075) | 1.34 | 1.34 |
| glue (EXP-0076) | 0.90 | 0.90 |
| **total** | 5.96 ms → 168 tok/s | **4.48 ms → 223 tok/s** |

Against the CPU's 31.62 ms at 16k: **7.1x**, up from 5.3x. The projection went
8.5x → 6.3x → 5.3x as unmeasured terms were added, and now **back up to 7.1x**
because one term got measured properly instead of estimated. That reversal is
the point: the earlier estimates were bounds built from plausible assumptions,
and the bucket table is a real kernel.

## 5. Conclusion

Keep. Two things this does not cover: the activation `x` is a single synthetic
row shared by all buckets, so real decode (where each matvec consumes the
previous layer's output) will serialise buckets that are independent here; and
prefill, where the same bucket structure serves many rows and the GEMM rather
than GEMV shape applies. Both are EXP-0078/A2.

The remaining 11% to ceiling is not launch cost — 5 launches is nothing. It is
the tail of each bucket's block count and the Infinity Cache serving the 393 MB
q4_K bucket at launch start.

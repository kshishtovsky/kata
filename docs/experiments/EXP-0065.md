# EXP-0065: prefill RoPE rebuilt the same tables 16384 times per layer

Status: PASSED (interval limit, no arithmetic change)

## Where the 614 ms went

`docs/experiments/EXP-0064.md` left the prefill `prep` stage measured at
**614 ms of a 16k run** while doing what looks like trivial elementwise work.
Three probes narrowed it down:

| probe | setup | result |
|---|---|---|
| `/tmp/prep.cpp` | the same work in isolation: 16384 rows x (2 `rope` + 1 KV write) | **19.0 ms** |
| `/tmp/prep3.cpp` | same, split | rms_norm 5.6 ms, rope+KV 18.4 ms |
| `/tmp/prep2.cpp` | same, 15 workers spinning vs yielding | 20.2 / 24.5 ms |

So the arithmetic is 19-24 ms and the engine spends 614 ms. The gap is the
call structure, not the math: `model.cpp:832-834` called `rope()` twice per row,
and each call ran `angles()` (`src/rope.cpp:36-52`), which **heap-allocates two
`std::vector<float>` and evaluates 64 `std::cos`/`std::sin` in double**. The
tables depend only on `(pos, head_dim, rope_base)`, so all 10 attention layers
re-derived the identical tables for the identical positions, 16384 rows deep,
single-threaded while 15 workers sat parked.

A reviewer run reached the same conclusion from the code alone and added the
second structural point: the loop was serial while every sibling stage is `_mt`.

## Change

- `src/rope.cpp`: new `rope_tab_avx2(...)`, identical rotation taking
  `const float * cos_t, const float * sin_t` instead of `(pos, theta_base)`;
  `rope_tab()` wrapper; `rope_table_range(head_dim, pos0, n_pos, base, cos, sin)`
  filling `[position][head_dim/2]` in one pass.
- `src/model.cpp`: `rope_cos` / `rope_sin` buffers sized once in `alloc()`;
  `attention_rows` builds the tables once per chunk, then rotates and writes KV
  in a `pool.run` banded over rows.
- `rope()` and `rope_ref()` keep their old signatures for the decode path and
  the existing tests.

Arithmetic is unchanged: same `std::cos`/`std::sin` in double, same AVX2
rotation, so results are bit-identical rather than merely close.

## Measurements

`prep` per 16384-token chunk, `KATA_PROF=1`, 16 threads:

| | before | after |
|---|---|---|
| prep per layer | 61.0 ms | **15.6-17.1 ms** |
| prep, 10 layers | ~614 ms | **~166 ms** |
| whole 16k prefill | 421.7 / 435.6 tok/s | **433.9 tok/s** |

544/522-token prefill: 519.3 → 527.1-541.9 tok/s (two runs each).
Golden point unchanged and identical before and after the change:
`argmax=17778 logit=28.35602` at 16k, `argmax=487 logit=15.80108` at 522.
105/105 tests pass.

## What this does not fix

The 16k prefill is still dominated by the attention core (`core 644 -> 1709 ms`
across the 10 layers), which EXP-0057 measured at 62% of the fp32 peak with
every lossless lever already tried. `prep` was 1.5% of the chunk; it is now
0.4%. The end-to-end move is 421.7-435.6 to 433.9, i.e. inside the run-to-run
band, and is recorded as such rather than claimed as a speedup.

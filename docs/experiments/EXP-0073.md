# EXP-0073 — q6_K on the GPU, and a whole decode token's weight traffic

**Status:** PASSED
**Date:** 2026-11-27

## 1. Problem

EXP-0072 put q4_K GEMV on the GPU and projected ~248 tok/s for decode, but q4_K
is only 70% of a token's weight traffic. The remaining 30% is q6_K (and a small
f16 tail). q6_K is also the format that already broke once: EXP-0026 got 0.61x
on VNNI because its 16 sub-blocks of 16 values double the epilogue relative to
q4_K's 8 of 32. If the GPU version has the same structural problem, the
projection collapses.

## 2. Hypothesis

A q6_K kernel that accumulates in integers per scale group — the same trick
that rescued the CPU version in EXP-0029 — should be correct and should land
near q4_K's rate on the GPU, because the GPU is not epilogue-bound the way a
VNNI dot instruction is.

## 3. Implementation

`gemv_q6_K_kernel` in `bench/bench_hip_gemv.cpp`. 8 threads per super-block,
each owning 4 consecutive `l` values in both halves (32 values per super-block),
32 super-blocks per 256-thread block so `nb <= 32` packs whole rows.

Integer accumulation per scale group: `q` in [-32,31] and `y` in [-127,127] make
a 4-term sum fit in int comfortably, and the scale multiply happens once per
group instead of once per value. `sc[is+0], sc[is+2], sc[is+4], sc[is+6]` are
constant per lane because `is = lane >> 2` and `l0 = lane * 4`, so 4 consecutive
`l` never cross a 16-value sub-block boundary.

## 4. Results

| tensor | shape | bytes | max\|abs\| vs CPU ref | GB/s |
|---|---|---|---|---|
| `blk.2.attn_v.weight` | 512x2048 (nb=8) | 0.9 MB | 3.576e-07 | 43.4 |
| `blk.0.ffn_down.weight` | 2048x11776 (nb=46) | 19.8 MB | 1.907e-06 | 290.6 |

Both correct. The 43.4 GB/s on the small tensor is launch-bound, not
bandwidth-bound — the same 0.9 MB would stream in 1.2 us at the ceiling.

## 5. The number that matters: one decode token

Both formats, one timed sweep, whole model, 4 of 64 experts (what a token
actually activates), 221 tensors:

```
DECODE SWEEP (4 of 64 experts): 221 tensors, 1517.6 MB (q4_K 1073 + q6_K 445), 3.72 ms
  408.3 GB/s (ceiling 764.3 -> 53%);  16.8 us per launch
  a decode token's weights alone: 3.72 ms -> 269 tok/s if everything else were free
```

Against **31.6 ms / 31.6 tok/s** on CPU at 16k depth, that is **8.5x** on the
weight-reading part of a token, measured rather than projected.

Decomposition: launch overhead is 2.77 us x 221 = 0.61 ms = **16%** of the
3.72 ms. Excluding it, the payload streams at 488 GB/s, i.e. 64% of the ceiling.
HIP graph replay was measured at 2.83 us/node, so batching commands does not
remove the overhead on this driver.

## 6. What this still does not include

The 3.72 ms is weights only. A real token also pays for: attention (the score
and PV passes over the KV cache — 337 MB/token at 16k on CPU, which was
ALU-bound there), MoE routing and dispatch, the KV cache write, RMSNorm, RoPE,
sampling, and the residual stream. Those are small in bytes but not necessarily
in time, and the CPU profile showed attention alone at 9.06 ms of a 31.62 ms
token at 16k.

Also unmeasured: PCIe. If the weights had to be transferred per token instead
of staying resident, the whole result inverts — the 14.5 GB model does not fit
through PCIe in 3.72 ms. This is why resident VRAM is an architectural
requirement, not an optimisation.

## 7. Conclusion

Both shipped quantisation formats now have a working GPU GEMV, correct to float
rounding. 53% of the read ceiling on a decode-shaped sweep, 16% of it eaten by
launch overhead that graphs do not fix. An 8.5x decode projection stands, with
attention and dispatch as the next unknowns.

Next: measure what attention costs on the GPU at 16k depth (currently 9.06 ms
of a 31.62 ms CPU token), because if it does not fall, it becomes the new floor.

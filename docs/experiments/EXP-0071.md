# EXP-0071 — Continuous batching: the curve, and the ceiling that bounds it

**Status:** PASSED (measurement)
**Date:** 2026-11-27
**Follows:** the user's directive (m09478) to measure the batch curve before
building a scheduler.

## Problem

Decode is at 93% of the memory ceiling (1529 MB/token at 68.3 GB/s), so a single
chat cannot get faster on this CPU. The remaining throughput lever is to read
each weight once and use it for several independent sequences. Nobody had
measured whether that actually pays here — the engine's `ModelState` holds only
`pos`, so B sequences already work through B `forward()` calls, but each call
reads every weight separately.

## Hypothesis

One forward pass over B independent rows reads every weight once, so B rows must
cost much less than B single-row passes. Expected: near-linear gain in rows/s
until the machine saturates.

## Implementation

`bench/bench_batch.cpp` (new, CMake target `bench_batch`). Two arms on identical
state:

- **baseline** — B separate `Model::forward(token, state)` calls, one state each;
- **batched** — one `Model::prefill_logits(tokens, B, state, out)` pass.

A third column is a traffic model built from the model shape, because an
achieved-GB/s figure that no kernel could reach is the tell for a bad harness:
`fixed 587 MB + KV + (union of selected experts) x 340 MB/layer`.

Two structural self-checks run at the end and exit 1 on failure: `batched(B=1)`
must be under 1.6x a decode pass, and per-row cost at `B=64` must be below
per-row cost at `B=1`.

**A harness bug was caught in this arm, and it changed the conclusion.** The
first version of the deep-context probe passed the SAME token B times, so every
row selected the same four experts and the union column was meaningless: it
reported 6.34x at B=16, of which roughly half was free expert-traffic
amortisation that a real workload never gets. With distinct tokens the honest
figure is 3.09x. The traffic model is what exposed it — 77.7 ms for a pass the
profile said was 165.8 ms.

## Analysis

**The naive baseline does not scale at all**, and that is the important negative
result: B independent decode rows cost 31.3-31.4 ms each at B=1, 8, 16 and 32 at
16k depth. There is no free lunch in calling `forward()` B times; the weight
traffic is simply paid B times. Every gain in both tables comes from the batched
path.

**Expert traffic, not row count, sets the ceiling.** On the 559-token prefix,
achieved bandwidth peaks at **52.3 GB/s at B=16** and falls to **41.3 GB/s at
B=64**. Selected experts saturate at all 64 by B≈32-64 while the fixed 587 MB
amortises over more rows, so added rows stop buying anything and the working set
leaves the 96 MB L3 (7.2 GB at B=16, 10.6 GB at B=64). The practical sweet spot
is **B=8-16**.

**At 16k depth the picture is better, not worse**, contrary to the expectation
that attention would eat the gain. Attention work per row is unchanged by
batching (each sequence has its own KV cache), yet speedup rises from 2.62x to
3.09x at B=16 because the weight-read share is larger at depth. The 16k profile
makes the split explicit: B=16 costs 165.8 ms with ffn 120.2 and attn_core 29.9,
against a single row's 54.0 ms with attn_core 22.9 — so attention is 18% of the
batched pass and 42% of a single-row pass.

**Batched B=1 is 1.7x slower than decode at 16k** (53.0 vs 30.9 ms): the chunked
path runs attention through `attention_prefill`, which at m=1 issues 22.9 ms
where the decode kernel needs 9 ms. This is the same m=1-GEMM penalty recorded in
EXP-0070's investigation (8.8x on matvecs). A server must therefore keep the
GEMV decode path for B=1 and switch to the batched path only above a threshold.

**Glue is 10% of a batched pass.** In the B=32 short-prefix profile,
`q8gather` (14.4 ms) plus `router` (2.5 ms) are pure overhead against 78.9 ms of
gate/up GEMM. This is the same class of accounting error that hid dispatch cost
for three iterations at m=1, and it is the cheapest place to look after the
scheduler exists.

## Conclusion

Continuous batching is worth building, with a measured target: **3.1x total
throughput at B=16 on a 16k prefix (31.7 -> 98.4 rows/s), 4.2x at B=32**. The
scheduler should target B=8-16, not larger, because expert traffic saturates and
L3 is exceeded past that. The B=1 path must stay on GEMV.

## Correction — what the batched arm actually is (added after review)

The batched arm calls `prefill_logits(tokens, B, state, out)`, and **`ModelState`
holds only `pos`** (`include/kata/model.h:11-13`) while the KV cache lives in
`Model::Impl` (`src/model.cpp:197`, `[n_layer][n_ctx][n_head_kv*head_dim]`). So
the B rows are a **B-token causal chunk written into one shared cache**, not B
independent sequences. Two probes in `/tmp` establish exactly what that means:

| probe | result |
|---|---|
| row 0 logits with row 1's token changed | `max|diff| = 0.000e+00` — row 0 is clean |
| row 1 logits with row 0's token changed | `max|diff| = 7.324` = **53.7%** of max logit |

Row 0 is a genuine decode step (causal attention gives it nothing but itself).
Every later row attends to the other rows' tokens and is therefore contaminated.

**This does not invalidate the timings, and it is worth being precise about why.**
The cost of a row is one decode step's weight traffic plus attention over the
full prefix: in the chunk, row `i` attends to 16770+`i` positions of the shared
cache, and in a real batch row `i` would attend to 16770 positions of its own
cache. The bytes read and the FMAs issued are the same to within `B/16770`
(0.1% at B=16). What the arm measures is the *work*, which is what a throughput
curve needs.

**But it overstates the amortisation, by the same mechanism as the same-token
bug.** Contaminated rows have hidden states mixed with their neighbours, so their
expert choices are more correlated than independent sequences would be, and
correlated experts are exactly what makes the union small. The honest figure is
therefore the *lower* of the two measurements taken here — and the same-token
probe (6.34x) versus distinct tokens (3.09x) shows how much that lever is worth.
3.09x must still be read as an upper bound on what a real scheduler delivers.

**The real prerequisite is a KV refactor.** B independent sequences need B
separate caches: 671 MB per sequence at 16k (10 layers x 8 kv-heads x 64 dim x
16384 x 4 B x 2), **10.7 GB at B=16** against the 96 MB L3 and 62 GB of RAM.
Today that is impossible without B full `Model` instances, i.e. B copies of the
14.5 GB of weights. Until the cache moves into `ModelState` (or into a
per-sequence slab owned by a scheduler), continuous batching has no
implementation to measure — only this cost model.

## Conclusion (corrected)

Continuous batching is worth building, and the measured work saving is real: one
pass over B rows costs 10.2 ms/row at B=16 against 30.9 ms/row for independent
decode at 16k depth. The number to plan against is **~3x at B=16**, not the 6.3x
a correlated-experts probe can produce. The next task is not the scheduler but
the KV-cache ownership change that makes B sequences representable at all.

## Review fixes (second pass)

A review of the committed harness found the traffic model was wrong in three
independent ways, and that the committed binary could not produce the 16k table
at all (`a.load(argv[1], 4096)` against a 16770-token prompt threw
`kata: context full`). All are fixed:

| error | effect | fix |
|---|---|---|
| `n_moe = 30` | expert traffic 0.79x low — the model has 38 MoE layers | `n_moe = 38` |
| q4_K charged to `ffn_down_exps` | 1.15x low — down is q6_K | separate 0.82 B/param |
| KV not scaled by B | **largest** error: 10.7 GB missing at B=16 | `B * kv_one_mb` |
| `n_ctx = 4096` | 16k arm impossible to run | `n_ctx = pos + 256` |
| baseline uses one token | leaves one expert slab hot, flatters the baseline | distinct tokens |

The corrected model now prints a GB/s column that is a real ceiling check, and it
immediately shows the shared-cache arm is **not physically achievable as a real
batch**:

| B | traffic/pass | memory floor | floor per row | ceiling rows/s |
|---|---|---|---|---|
| 1 | 2209 MB | 30 ms | 30.1 | 33.3 |
| 4 | 6737 MB | 92 ms | 22.9 | 43.6 |
| 8 | 12091 MB | 165 ms | 20.6 | 48.6 |
| 16 | 21171 MB | 288 ms | 18.0 | 55.5 |
| 32 | 35583 MB | 484 ms | 15.1 | 66.1 |

Measured batched B=16 at 16k depth is **163.6 ms**, which is *below* the 288 ms
floor — impossible for a real batch, because the shared cache charges KV once
instead of 16 times. So the honest statement is: a real B=16 batch on CPU tops
out at **55 rows/s (1.75x over today's 31.6)**, not the 98 rows/s the shared-cache
arm reports. Expert union at B=16 is the remaining lever: at 41 of 64 experts the
expert term is 251 MB/row of the 1323 MB/row total.

## The real ceiling: the GPU is idle and 10.4x faster

Measured with HIP on the installed RX 7900 XT (`/tmp/bwr.hip`, read-only probe over
4 GiB, well past the 96 MB L3):

- **GPU read-only bandwidth 764.3 GB/s against the CPU's 73.5 GB/s = 10.4x.**
- Decode reads 1538.9 MB of weights per token, so the GPU memory floor is
  **2.01 ms/token = 496 tok/s**, against 31.6 ms today at 16k depth.
- The model is 14.5 GB and VRAM is 20 GB, so all weights fit resident with
  ~5.5 GB left for KV (a 16k sequence needs 671 MB).
- Compute is not the constraint: ~2.7 G active values per token is 5.4 GFLOP,
  about 0.14 ms at fp32 peak.

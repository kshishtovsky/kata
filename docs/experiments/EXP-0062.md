# EXP-0062: the `{1to16}` weight broadcast is not expressible for q4_K VNNI

Status: FAILED, reverted

## Hypothesis

EXP-0061 found one `vpbroadcastd` per `vpdpbusd` in `q4_K_vnni_tile`, which caps the
shape at 50% of the VNNI peak. If the broadcast could ride inside the multiply as a
memory operand (the `m32bcst` form), the instruction count would halve and the kernel
should approach ~100% of the peak.

## What was built

`/tmp/bcst.cpp` compiled three forms and inspected the generated code:

    form_a  uint32 in a byte array, memcpy, set1_epi32   -> vpbroadcastd + vpdpbusd
    form_b  uint32 in a uint32 array, set1_epi32         -> vpbroadcastd + vpdpbusd
    form_c  inline asm "vpdpbusd %1%{1to16%}, %2, %0"    -> vpdpbusd mem{1to16}

So GCC never folds it, but the explicit form does exist. Applied to the real kernel it
compiled to **0 `vpbroadcastd` and 64 `vpdpbusd {...}{1to16}`**, exactly as intended.

## Why it is wrong

`VPDPBUSDS zmm1, zmm2, zmm3/m512/m32bcst` puts the unsigned operand in src1 and allows
the broadcast only on **src2**. kata's operands are weights-unsigned in src1 and
activations-signed in src2, so `{1to16}` broadcasts the activations, not the weights.

The unit probe (`/tmp/bcn5.cpp`, weights `0x00000001`, activations `0x04030201`) returned
1 for both forms — a degenerate case that cannot distinguish which operand got the
broadcast, which is why it passed. `GemmQ4K.MatchesPerRowGemv` caught it immediately:
relative error 11.2, 31.9, 22.2, 32.4, 24.4, 32.7 against a 1e-5 tolerance.

## Why it would not have helped anyway

Even in the numerically wrong form the kernel measured **2762 GMAC/s at m=512 (55.5%
of peak)** against the baseline 2727 (54.8%) — inside run-to-run noise. Removing the
broadcast does not move the needle, so the 50% arithmetic ceiling was not the binding
constraint either.

## Conclusion

The only way to use `m32bcst` is to swap the operand roles: weights as **signed**
(nibble - 8, which q4_K already corrects through the min term) and activations as
**unsigned** (q + 128, which adds a correction term needing `bsum`). That is a rewrite
of the pack format for a lever that measured neutral. Closed until the pack format is
already being changed for another reason.

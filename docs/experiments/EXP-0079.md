# EXP-0079 — Model and GGUF test suites; a rollback bug they found

**Status:** PASSED
**Date:** 2026-11-27

## Problem

`src/model.cpp` was the largest file in the project (904 lines) and sat at
1.44% coverage, because exercising it needs a GGUF with a real architecture.
`src/gguf.cpp` was at 44.63% after EXP-0078, with every error path untested.
The honest project total was 62.06% against the ≥75% floor.

## What was added

`tests/test_gguf.cpp` (9 tests) builds synthetic GGUF files byte by byte, so the
paths a 14 GB model made unreachable are now cheap: bad magic, unsupported
version, missing file, missing key throwing instead of returning 0, truncated
data section, per-tensor data pointers in range and distinct, alignment
fallback.

`tests/test_model.cpp` (21 tests) uses the 8B model (`KATA_TEST_MODEL`
override, default `/home/medovarov/models/gguf/LFM2.5-8B-A1B-Q4_K_M.gguf`) and
skips cleanly when absent: finite logits, determinism across reset, context
limit, vocabulary rejection, prefill position accounting, `prefill_logits`
row fill and non-reentrancy, ray of truncate paths, perplexity repeatability,
heatmap accounting, routing-record shape.

## The bug

`Model.TruncateThenReplayReproducesTheSameLogits` failed with `max|diff| 12.4`
on the replayed token. Root cause in `src/model.cpp` `shortconv_rows`:

```cpp
std::memcpy(conv_seq.data() + il * (ubatch + d_conv) * nc, seq, ...);  // BEFORE
std::memcpy(seq, hist, d_conv * nc * sizeof(float));                   // history copy
```

The snapshot was taken before the history was spliced in, so `conv_seq`'s first
`d_conv` rows held the *previous layer's* leftover `bx`, not this layer's
history. Rolling back to the chunk start therefore restored garbage. Fix: move
the snapshot after the history copy, so `seq` holds `[history][chunk bx]`,
which is what `conv_seq` claims to be.

This mattered because a speculative rollback at the chunk boundary is exactly
the case `truncate` exists for, and it was silently wrong — no crash, no NaN,
just a different continuation.

## Note on the prefill-vs-decode test

The first version asserted argmax equality between a token-by-token `forward`
and a batched `prefill_logits`. It cannot hold: decode runs GEMV and prefill
runs a chunked GEMM, so floats are summed in different orders and a near-tie
flips. Measured `max|diff|` is 0.85 (24B, 559 tokens) to 5.7 (8B, 5 tokens) on
a ~17 peak, with argmax matching on 12 of 16 rows for the 24B model. The test
now asserts finiteness plus a gross tolerance of 20, which catches a wrong
weight or a broken norm and nothing else.

The same mistake bit a `/tmp` probe: `prefill_logits(toks, n, st, out)` writes
*n* rows, and passing a single-row buffer overran the heap
(`munmap_chunk(): invalid pointer`). Fixed in the test, and it is why the
signature takes a caller-owned buffer rather than returning one.

# EXP-0083 — the whole token's weight stream, everything resident

**Status:** PASSED
**Date:** 2026-11-27

## Problem

EXP-0082 priced the MoE stage alone: 930 MB of experts in 1.690 ms on the GPU,
8.40x the CPU. But a token also reads 652 MB of non-expert weights, and every
projection so far has shrunk as an unmeasured term got measured (8.5x -> 6.3x ->
5.3x in EXP-0076, back to 7.1x in EXP-0077). So the honest question is what one
token's **entire** weight stream costs when nothing has to be transferred.

With the model measured at 14.52 GB (14518008320 B, of which 13.84 GB is MoE
experts, `gguf == 14.52 GB`) it fits in the card's 20 GB with room for KV, so this
is the shape a real backend would run.

## Method

`bench/hip/bench_token_gpu.hip` (`hipcc -O3 bench/hip/bench_token_gpu.hip -o
kata-work/bin/tkg -I include -L build -lkata_core -lpthread`):

- walks every q4_K (type 12) and q6_K (type 14) tensor in the GGUF;
- charges `n_bytes` for dense tensors and `n_bytes / n_expert` per picked slab;
- picks 4 random slabs per expert tensor (the real top-4 routing), so the stream is
  exactly one token's traffic: **fixed 652.3 MB + experts 865.3 MB = 1517.6 MB**;
- lays each **(format, nb) bucket** out contiguously in one host blob, uploads once
  (85 ms at 18.0 GB/s — load time, not per token), and runs **one launch per bucket**;
- verifies every bucket against `vec_dot_q4_K_q8_K_ref` / `vec_dot_q6_K_q8_K_ref`
  before timing.

The kernels are the ones verified in EXP-0072/0073; the q4_K one uses 4 lanes per
super-block (one 32-byte group of `qs` each) and `rpb = nb <= 64 ? 64 / nb : 1`.

## Result

```
5 buckets: q4/nb=6 x163840 rows  q4/nb=8 x808448  q6/nb=6 x147456  q6/nb=8 x130560  q6/nb=46 x4096

verify q4_K nb=6 rows=163840: max|diff| 2.384e-06 on 5.890e+00 (4.0e-07 rel) PASS
verify q6_K nb=6 rows=147456: max|diff| 4.768e-07 on 5.157e+00 (9.2e-08 rel) PASS

FULL TOKEN, everything resident: 3.241 ms in 5 launches
  468.3 GB/s | launches cost 0.014 ms | payload 3.227 ms = 470.3 GB/s
  -> 309 tok/s of weight streaming alone
```

Launch overhead is now **14 us for the whole token** — it stopped existing as a term.

| stage | CPU (559-tok prefix) | GPU |
|---|---|---|
| weights, full token | — | **3.241 ms** |
| weights, 221 launches (one per tensor) | — | 4.312 ms (410 GB/s payload) |
| weights, 563 launches (one per slab) | — | 6.49 ms (234 GB/s payload) |
| MoE stage | 14.20 ms | 1.690 ms (EXP-0082) |
| whole decode token | 22.55 ms | ≤ 3.24 + attention + glue |

## Conclusions

- **Launch count is the whole story: 563 -> 221 -> 5 launches moved the same
  1517.6 MB from 234 to 470 GB/s of payload, 2.0x, with byte-identical arithmetic.**
  The first version was not slow because the kernel was slow; it was slow because
  each launch's grid was too small to fill 84 CUs.
- `nb` is the only key the bucketing needs. Tensors of different shapes share a
  bucket freely because the row is what a block walks, and a bucket's rows are
  independent.
- 470 GB/s is 62% of the 764 GB/s ceiling measured in EXP-0071. The remaining gap is
  the q6_K `nb=46` bucket (4096 rows, 8 rows per block = 512 blocks) and the small
  `nb=6` buckets; those are the ones a real implementation would widen by merging
  the activation row into a multi-row pass, not the bulk q4 buckets.
- Token at 16k, every term now measured: weights 3.24 + attention 1.34 (EXP-0074)
  + glue 0.90 (EXP-0076) = **5.48 ms = 182 tok/s**, against the CPU's 31.62 ms.
  The projection has converged: three independent probes (EXP-0074, 0077, 0082)
  now agree with this one within 10%.

## Bugs found

1. **The q6_K bucket kernel was wrong when written from scratch.** A nibble
   shortcut (`off >> 1`) gave `max|diff| 2.519e+01 on 6.304e+00 (4.0e+00 rel)` at
   full speed. Fixed by copying the verified EXP-0073 mapping: 8 lanes per
   super-block, `is = lane >> 2`, `l0 = lane * 4`, per half
   `ql[half*64] / qh[half*32] / q8[half*128]`, `q1 = (qlb & 0x0f) | ((qhb & 3) << 4) - 32`,
   `q2` from `ql[l+32] & 0x0f` with `(qhb >> 2) & 3`, `q3 = qlb >> 4` with `(qhb >> 4) & 3`,
   `q4 = ql[l+32] >> 4` with `(qhb >> 6) & 3`, scales `sc[is+0], sc[is+2], sc[is+4], sc[is+6]`.
   A wrong kernel that runs at full speed and returns plausible magnitudes is the
   failure mode this verification pass exists for.
2. **Host offsets were passed to the GPU as pointers.** After bucketing, `streams`
   holds byte offsets for the host-side verification and `dev` holds the rebased
   device pointers. Launching from `streams` faulted at `address 0x28000` =
   163840 = exactly the first bucket's offset.
3. **A bucket-sized output buffer.** `dout` was sized `max(rows_n)` over the
   streams, but the biggest bucket has 808448 rows against a largest single tensor's
   4096 — the q4 `nb=8` bucket wrote 800 K floats past the allocation
   (`Memory access fault ... Page not present`).
4. `const size_t total_b` was declared twice (summary vs stream size) — renamed the
   stream one to `stream_b`.
